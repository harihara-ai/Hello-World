## Root causes behind the new findings

- RC-E is closed only on paper: red_check reads one exit code from the whole suite, so "fails on base" also means "does not load on base", and nothing re-runs the base suite on the new code (R2-4-01, R2-4-02).
- RC-D residue: the approval is not bound to one code PR. The PR chooses which approved plan governs it (`--change auto`), and a plan PR can carry code because `ready` never looks outside the change folder (R2-4-03, R2-4-04).
- RC-C residue: the PR still decides what coverage measures, through config files the PROTECTED list does not name (R2-4-05).

```
id: R2-4-01
severity: blocker
location: workspace/kit/gates/red_check.py check (on_base != 0 counts as red)
evidence: t5: `sed -i 's/\* 0.05/* 0.5/' src/cart.py`, every assert removed from tests/test_cart.py -> CI done PASS, red_check {'exit_base': 1, 'exit_head': 0}; base run fails with AttributeError (no bulk_discount on base).
problem: Any story or bug that adds a symbol is "red" on base because its tests cannot load there (import error, missing attribute, or a compile error in Java/C#), so assertion-free tests and wrong behaviour pass all gates; R2-3-05 is still open for the common case.
proposed_fix: Count red only from assertion failures per test, read from the runner's JUnit file (CI adds its path to --test-cmd's output via one flag, --test-report, because an exit code cannot tell an assertion from a missing symbol); when the tests do not load on base, run them on the PR's first commit (TDD order: tests and stubs first) and require an assertion failure there.
confidence: medium
```

```

severity: blocker
location: workspace/kit/gates/red_check.py; spec 10.4 #7 "Baseline suite still green" (S)
evidence: r1, scan ["src/cart.py","tests/test_cart.py","tests/test_base.py"]: subtotal loses its rounding (`round(...)` -> 2.5x3 = 8), test_base assertEqual weakened to `> 0` -> CI done PASS, all gates true.
```
